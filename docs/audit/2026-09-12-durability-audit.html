Quality assessment & engineering report

DuraQ Durability Audit

package duraq 1.0.1 commit 5315698 Dart 3.11.5 · macOS arm64 reviewed 12 Sep 2026

The structure is sound and the SQLite schema is well chosen, but DuraQ does not currently hold the guarantees its README advertises. Six defects can lose or duplicate a job, and one of them is already failing in the repository's own test suite.

Critical defects

C1–C6 · job loss or duplication

Each of these was reproduced against this commit. Every claim below comes from a run, not a reading.

C1Critical

Overlapping transactions roll back each other's committed work

Transaction nesting is tracked by a single integer on the storage object, while the transaction method itself is asynchronous. Two callers that overlap therefore nest inside one another by accident: the second caller's savepoint is taken after the first has already started writing, so the second caller's rollback discards the first caller's rows. The first caller still returns normally.

ReproducedTwo concurrent transactions, one storing a row and one throwing.

txn B failed as expected: Bad state: this transaction fails txn A reported success rows persisted: []

FixSerialize storage operations through a single-slot lock, and recognise a nested transaction only when it comes from the same logical caller, for example by issuing a token from begin rather than counting depth globally.

C2Critical

Parallel consumers are told the queue is empty while jobs wait in it

The same interleaving corrupts retrieval. Ten parallel retrieve calls against five pending entries hand out three, return null seven times, and leave two entries pending. A worker pool reads those nulls as an idle queue and backs off while work sits there.

ReproducedDeterministic across runs, and already failing in the repository.

test/storage/concurrent_processing_test.dart "should handle multiple concurrent queue operations" Expected: <5> Actual: <3> handed to workers: [e0, e2, e4] e1: pending e3: pending (never offered)

FixMake a claim atomic: one statement that selects and marks in a single step, or a serialized critical section around the claim. This is the same root cause as C1 and both close together.

C3Critical

Retry backoff is calculated, stored, and then ignored

On failure the queue computes a delay and writes it to the entry, but neither backend's retrieval predicate reads that column. The candidate query filters on scheduled time and expiry only. A failed job returns to pending and is immediately eligible again, so a permanently failing job spins at full speed through its whole attempt budget instead of backing off. Exponential backoff is a headline feature and it has no effect on either backend.

ReproducedTen-minute base delay, SQLite and Isar alike.

after failure: status=pending attempts=1 nextRetryAt=2026-09-12 11:00:53 immediate retrieve returns the same entry

FixAdd the retry gate to the candidate query on both backends and index it. The SQLite index for it already exists and is unused. Note that the insert statement also omits the retry column entirely, so a pre-built entry loses the value before it is ever read.

C4Critical

Nothing ever recovers an entry left in processing

Retrieval marks an entry as processing and takes a five minute lock. If the worker crashes, the process is killed, or the caller used dequeue, that row stays processing forever. The lock expires; the status does not. No query looks at processing rows again, so the job is unreachable, and the queue reports its length as zero. For a library whose purpose is surviving restarts, this is the most consequential gap in the design.

ReproducedRetrieve an entry, then simulate the worker dying.

next retrieve: null ; queue length = 0 row status now: processing (no reaper exists)

FixIntroduce a visibility timeout. Persist the lease expiry on the entry itself and let retrieval reclaim processing rows whose lease has passed, bounded by the attempt count so a poisonous job still reaches the dead letter queue. Expose an explicit reclaim call for startup.

C5Critical

Isar stores one job many times and delivers it many times

The entry identifier carries a non-unique index and the collection uses an auto-incrementing primary key, so storing the same entry twice creates two independent rows. Counting sees both. Status updates find only the first. The processor runs on the payload once per row, which turns a retried enqueue or a replayed request into duplicate side effects.

ReproducedOne entry stored twice, then drained through the queue.

payload delivered to the processor 2 time(s) for one logical job rows: same-id completed · same-id processing (stranded)

FixPut a unique composite index on queue name and entry id, and write through it. Then settle the contract that SQLite and Isar currently disagree about, described in H7.

C6Critical

The Isar transaction API provides no atomicity at all

Begin, commit and rollback only move a counter, and rollback does nothing else. Each individual write has already committed in its own write transaction, so a multi-step operation that throws halfway leaves the earlier steps in place. Callers get the same method signature as the SQLite backend and a different guarantee. The README carries a note about this, but the interface still promises atomicity and rollback still returns success.

ReproducedA transaction that stores a row, then throws.

transaction threw: Bad state: rollback please rows after rolled-back transaction: [a]

FixRun the body inside one Isar write transaction and have the storage methods join the ambient transaction instead of opening their own. Until that lands, make rollback throw rather than pretend.

High severity

H1–H7 · correctness under load and across processes
H1High

Disposing one storage instance releases every lock in the database

The release-all path is an unfiltered delete over the lock table, and disposal calls it. Any process, isolate, or component shutting down therefore drops the locks held by every other consumer of the same file, across every queue in it. The next retrieval can hand out an entry that is still in flight elsewhere.

FixTrack the lock identifiers this instance owns and delete only those, or leave the lock table alone on disposal and let leases expire.

H2High

Locks have an owner identifier that is never checked

Acquiring a lock generates and stores an identifier and returns it, but nothing keeps it and release deletes by queue and entry alone. A worker whose lease has already expired will happily release its successor's lock when it finishes, and any caller can release any lock through a status update. The identifier gives the appearance of ownership without enforcing it.

FixCarry the lock identifier with the claimed entry and make release conditional on it.

H3High

Multi-process use is not configured for, and fails loudly

Write-ahead logging is enabled, which invites multi-process use, but the busy timeout is left at zero. A second process writing the same file gets an immediate locked error rather than waiting. Disposal can fail the same way and throw out of a shutdown path.

MeasuredTwo processes, 300 enqueues each, same database file.

B: committed=253 failed=47 SqliteException(5): database is locked (a second run crashed the losing process inside dispose)

FixSet a busy timeout, retry on contention, and state the supported concurrency model in the README. Several projects sharing one queue file is exactly the situation this package invites.

H4High

Every dequeue rescans the entire backlog before it looks for work

Retrieval runs an expiry sweep across all pending rows of the queue on each call, even though the candidate query that follows already excludes expired rows. The sweep cannot use the partial expiry index and falls back to the retrieval index, so its cost is proportional to the backlog. At twenty thousand pending entries it is almost the entire cost of a dequeue.

MeasuredBacklog of 20,000, no row carrying an expiry at all.

expiry sweep 1086 us per dequeue candidate select 52 us lock cleanup 5 us

FixTake the sweep out of the hot path and run it in periodic maintenance. The candidate query already handles expiry lazily. While there, replace the offset-walking loop that searches for an unlocked candidate, which rescans from the start on each attempt.

H5High

The Isar backend declares ten indexes and uses none of them

All twenty-one queries in the Isar backend go through the unindexed filter path, which walks the whole collection and sorts the matches in memory; not one uses an indexed lookup. The model meanwhile declares ten indexes, including a composite retrieval key no query mentions. They cost write time on every store and return nothing on read. Isar enqueues at roughly a sixth of SQLite's rate.

FixQuery through the composite index that already exists and delete the ones nothing reads.

H6High

Finished work is never removed

Nothing deletes completed, failed, or dead-lettered rows. The one cleanup routine covers expired entries only, exists on the concrete classes rather than the storage interface, and is never called by the library or reachable through it generically. A queue that runs for months keeps every job it has ever processed.

FixPut a retention policy and a maintenance entry point on the interface, and document who is expected to run it and how often.

H7High

The two backends disagree about storing a duplicate identifier

SQLite throws a raw driver exception with the failing statement and parameters attached; Isar silently creates a second row. A caller writing against the interface cannot handle both, and the payload appears in the SQLite error text, which is a logging concern of its own.

FixDecide whether store is an upsert or an error, implement it identically on both backends, translate driver exceptions into a package-level error type, and test the contract against every backend.

Medium severity

M1–M14 · contract, clarity, and dead weight
M1Medium

dequeue does not remove anything

Documented as retrieving and removing, it marks the entry as processing and returns the payload with no way to acknowledge it. Every call leaks a row by the mechanism in C4. Either implement it as claim-and-delete or retire it in favour of the processing callback.

M2Medium

Queue manager caches by name and casts

Asking for the same queue with a different element type throws a type error, and the first caller's type wins for the lifetime of the process. A queue first touched without a type argument can never be fetched with one.

M3Medium

Type safety is nominal

Payloads round-trip through JSON, so a plain Dart object throws at enqueue and a mismatched type surfaces as a cast error at dequeue. The feature list promises generic support for any data type. A codec parameter on the queue would make the constraint explicit and lift it.

M4Medium

Storing an entry drops its retry time

The insert statement omits the retry column, so a pre-built entry carrying one loses it silently. Confirmed by round-tripping an entry through store and read-back.

M5Medium

Backoff arithmetic overflows into a negative delay

The delay is a power of two with no bound on the exponent. At 60 attempts it returns a negative duration, which schedules the retry in the past, and beyond about a thousand it returns zero. The maximum delay is bypassed in both cases because the clamp compares against the overflowed value.

M6Medium

Status updates clear fields nobody asked them to clear

Each update overwrites the error message and retry time with null unless both are supplied, and no update checks that a row matched, so a wrong identifier is a silent success.

M7Medium

Queue length counts jobs that cannot be dequeued

Entries scheduled for the future and entries waiting on a retry are both counted as pending. A queue reporting a length of one can return nothing on the next call, which makes the figure unsafe for health checks or scaling decisions.

M8Medium

Dead-lettered and expired entries keep their lock

Lock release covers the completed, failed and pending transitions only, so those two paths hold a lease for its full duration after the entry is finished with.

M9Medium

Metrics and health checks are inert

No code in the library records a metric, so every rate reads as zero. The metrics health check probes a hardcoded queue name and is therefore always healthy, and the queue health check reads a queue called default. As shipped, the health surface reports nothing about the running system.

M10Medium

Lock acquisition swallows every error as contention

Any exception, including a genuine storage failure, is reported as "already locked", which then drives the candidate scan forward instead of surfacing the problem.

M11Medium

The storage interface has no teardown

Neither dispose nor close appears on the interface, and the two implementations differ in shape, one synchronous and one asynchronous. Backend-agnostic shutdown is not expressible.

M12Medium

Isar is a hard dependency for everyone

A project using only the SQLite backend still pulls Isar and its native core, and is pinned to a version whose generated code already raises analyzer warnings on current Dart. Splitting the Isar backend into its own package removes that from every SQLite consumer.

M13Medium

No schema version, no migration path

Tables are created if absent and never versioned, and an unrecognised status string throws when a row is read. Any future column or status value has no safe way to reach databases already in the field.

M14Medium

Durability is one notch below what the name suggests

The database runs write-ahead logging at normal synchronisation, so recently committed jobs can be lost on an operating system crash or power loss. That is a reasonable default, but a package called DuraQ should say so and let the caller ask for full synchronisation.

Performance

measured on this machine, single process

Both backends slow down as the backlog grows, which is the opposite of what a queue should do: the deeper the queue, the slower it drains. The cause is different in each, and in both cases it is avoidable work rather than a storage limit.

Test suite and process

Q1–Q6
Q1Critical

The published version does not pass its own tests

On a clean checkout of this commit, the concurrent processing test fails deterministically. A release went out with a red suite, which means the suite is not gating anything.

Q2High

Coverage is thinnest exactly where the risk is

Overall line coverage of the library is 48.7 per cent excluding generated code, and the two storage backends, which hold nearly all the complexity, are the least covered files of any real size.

Q3High

The isolation test cannot fail

The transaction suite's isolation step runs two concurrent transactions and then asserts that it received two futures. It passes while isolation is broken, which is how C1 survived to release. The durability step in the same test reopens the file in the same process, which does not exercise durability either.

Q4High

No continuous integration and no lint configuration

There is no workflow directory, so nothing runs the suite on a push. There is also no analyzer configuration, so the lints package listed as a dev dependency is never applied. The analyzer reports 40 issues under its defaults, including two deprecated calls on the lock path.

Q5Medium

The untested behaviours are the ones that fail

Nothing covers crash recovery, retry timing, lease expiry, multi-process access, duplicate identifiers, dead-letter lock release, the time-to-live of an in-flight entry, or behaviour at any real backlog size. Every critical defect in this report sits in that gap.

Q6Medium

Tests lean on real databases and wall-clock waits

The mock storage helper is present but unused, and timing-sensitive assertions rely on real delays. Both will make the suite flaky the moment it runs on shared continuous integration hardware.

What holds up

keep these decisions

The layering is right

Queue, storage interface, retry policy and dead letter queue are cleanly separated, which is why most of the fixes below are local.

The SQL is parameterised throughout

No string interpolation of user data anywhere in either backend.

The SQLite schema is well chosen

The composite retrieval index matches the query, and the partial indexes are the right instinct. One of them just needs the column order that would let the planner use it.

The dead letter API is complete

Retrieve, list with paging, retry, remove and purge, all covered by tests and the best-tested area of the package.

Savepoint nesting is the correct mechanism

The idea is sound; only the bookkeeping that decides when a savepoint is nested needs replacing.

The recent fixes were real

Releasing the lock when an entry is retried back to pending, and widening the driver constraint, both addressed genuine problems.

Suggested order of work

dependencies first

  1. Serialize access to the storage object

    A single-slot lock around storage operations closes the interleaving that causes both the transaction corruption and the phantom-empty queue, and removes the races underneath several lock findings. C1 · C2 · H2

  2. Make a claim recoverable

    Honour the retry time in the candidate query, persist the lease on the entry, and reclaim expired leases on retrieval and at startup. This is what turns the package durable in the sense the name promises. C3 · C4 · M1 · M4

  3. Give Isar a unique entry and a real transaction

    A unique composite index stops duplicate delivery; scoping the transaction body to one write transaction restores atomicity. If neither is worth the effort, the honest alternative is to withdraw the backend. C5 · C6 · M12

  4. Take avoidable work out of the dequeue path

    Move the expiry sweep to maintenance, replace the offset walk, and let the Isar queries use the indexes the model already declares. H4 · H5

  5. Define the lifecycle at the interface

    Retention and maintenance, teardown, a package-level error type, and one agreed answer to storing a duplicate identifier. H6 · H7 · M11

  6. Configure for the concurrency you invite

    Busy timeout and contention retries, lock release scoped to the owner, and a README section stating what is supported across processes and what is not. H1 · H3 · M14

  7. Put a gate in front of the next release

    Continuous integration on every push, an analyzer configuration that applies the lints already listed as a dependency, and a regression test for each defect above, starting with the one that is red today. Q1 · Q4 · Q5

Method. Every defect was reproduced against commit 5315698 with standalone programs driving the public API, and the query-plan and timing figures come from the same database files the library creates. Benchmarks ran single-process on Dart 3.11.5, macOS arm64, with one job per operation; they are useful as relative shape, not as absolute numbers for other hardware.

Scope. The review covers the library source, its test suite, and the README's claims. Generated Isar code was read but not audited. No fixes were applied to the repository.
